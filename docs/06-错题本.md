# 06 · 错题本

> 踩过的坑，逐条记录在案。**新坑必须落到这一页**，不许只活在某个会话的记忆里。
> 排错手册（按症状查）见 [`05-故障排查.md`](05-故障排查.md)；本错题本是它的**事实来源**——
> 排查手册讲"这类症状通常是什么"，错题本讲"我们确实踩过哪一条、什么时候、证据是什么"。

---

## 怎么用这本账

| 时机 | 动作 |
|---|---|
| 每次踩新坑（修完那一刻） | 在下面加一条，编号顺延，写全六栏 |
| 每次会话结束 | 扫一眼有没有"修了但没记账"的 |
| 改脚本/文档时 | 如果某条错题被永久修好了（不是绕开），把状态改 `已根治` 并注明修法 |

**每条必须有的六栏**：

```
### E<编号> · <一句话标题>
- 日期 / 环境  ：何时、在哪台机器哪个工作空间踩的
- 症状         ：看到什么现象（含报错原文）
- 根因         ：为什么会这样（[实测] / [推断] 标注）
- 修法         ：具体怎么修（命令或改法）
- 证据         ：文件路径 / 日志 / 实测数值
- 状态         ：已根治 / 已绕开 / 待办 / 观察
```

> 铁律：**测不了就写"未验证"**，不许用推断冒充实测。

## 2026-10-15 · Ideaform 工作空间磨合实录

### E01 · remotion.config.ts 写死 chrome 路径，换机器/清缓存即失效
- **日期 / 环境**：2026-10-15 · Ubuntu 26.04 WSL2 · `~/tools/remotion-app`
- **症状**：`remotion.config.ts` 里 `Config.setBrowserExecutable("<写死的本机绝对路径>/chrome-headless-shell")`
  指向的目录已不存在；不修则 `remotion still/render` 直接报
  `browserExecutable ... but the path doesn't exist`。
- **根因** `[实测]`：早期模板把 chrome 绝对路径写进了配置，而 Remotion/puppeteer
  缓存的 chrome 实际在 `node_modules/.remotion/chrome-headless-shell/...` 下，两者会漂移。
- **修法**：模板里**不写死**，改为
  `if (process.env.VW_CHROME) Config.setBrowserExecutable(process.env.VW_CHROME);`
  然后 `detect.py --write` 刷新契约（`tools.remotion.browser.resolved`），
  渲染时带 `--browser-executable "$VW_CHROME"`。
- **证据**：detect.py 本轮输出 `· chrome △ 已失效→已重新定位 .../.remotion/chrome-headless-shell/linux64/chrome-headless-shell-linux64/chrome-headless-shell`；
  该文件实测存在（219 MB，`-rwxr-xr-x`）。
- **状态**：已根治（自带模板已走环境变量；`render-segments.sh` 自动带 `--browser-executable`）

### E02 · LMMS 装在旧日期工作空间里，契约"机器级"的假设有漏洞
- **日期 / 环境**：2026-10-15 · `~/WorkBuddy/2026-10-09-20-23-11/lmms-lab/`
- **症状**：`detect.py` 探到的 LMMS AppRun 是
  `~/WorkBuddy/<旧日期工作空间>/lmms-lab/squashfs-root/AppRun` ——
  在另一个**日期工作空间**内。哪天那个工作空间被清理，LMMS 就"凭空消失"，
  而契约还指着它。
- **根因** `[实测]`：install.sh 的设计本就是装到 `$VW_CONFIG_ROOT/lmms/`
  （机器级、不随工作空间消亡），但本机的 LMMS 是早期手工解包到工作空间的，
  绕过了设计路径。文档宣称"契约是机器级的，换工作空间不用重配"——
  这话只在**工具本身也装在机器级路径**时成立。
- **修法**：重装/迁移到 `~/.config/ideaform/lmms/`：
  `bash skills/ideaform-setup/scripts/install.sh --only lmms`（会先备份 `.lmmsrc.xml`），
  再 `detect.py --write`。迁移前旧目录保持不动（双保险）。
- **证据**：`ls` 确认 AppRun 存在；契约 `tools.lmms.apprun` 指向该路径；
  `tools.lmms.stkdir_ok = true`。
- **状态**：待办（旧位置仍可用，列为清理工作空间前必须处理的依赖）

### E03 · 直接 `node .bin/remotion render` 报 No entry point specified
- **日期 / 环境**：2026-10-15 · `render-segments.sh` 首跑
- **症状**：`node <proj>/node_modules/.bin/remotion render <Comp> out.mp4` 报
  `No entry point specified. Pass more arguments: npx remotion render [entry-point] ...`
- **根因** `[实测]`：Remotion CLI 靠 **cwd** 发现 entry point（`src/index.ts` /
  `remotion.config.ts`）。`npx remotion` 在项目目录下跑所以无感；
  裸 `node .bin/remotion` 在别处跑就丢 entry point。
  （`verify.py` 的 still 检查是在 `cwd=proj` 下跑的，所以没暴露这个问题。）
- **修法**：渲染一律包在子 shell 里：`( cd "$PROJ" && node "$CLI" render ... )`，
  且所有路径先转绝对路径。
- **证据**：`render-segments.sh` 首跑失败日志 `.tmp/.segments-throughput-test/chunk_000.log`；
  修复后重跑通过。
- **状态**：已根治

### E04 · 冒烟校验不是 90 秒，是 6.7 秒（热缓存）
- **日期 / 环境**：2026-10-15 · Ideaform 工作空间
- **症状**：`docs/02-工作流总览.md` 写"冒烟校验 ~90 s（其中 Remotion 渲 1 帧约 60 s）"，
  本轮实测 **6.715 s** 四项全过。
- **根因** `[实测]`：90 s 是**冷启动**（首次装依赖 / 首次拉 chrome / 冷 bundle 缓存）。
  热缓存下（node_modules 已在、chrome 已解包、TMPDIR 正确）单帧 still 约 2 s。
- **修法**：不需要"修"——这是**提速的根据**：复用常驻 Remotion 工程，
  不要每个工作空间重搭。已在 `docs/02` 补注冷/热两种数。
- **证据**：`.tmp/smoke-run1.log`（`real 0m6.715s`）；
  `report.json`：TTS 36144 B / still 1920×1080 1149335 B / LMMS 4.0 s 峰值 0.8123 /
  mux 190296 bps。
- **状态**：已根治（文档数据已更正）

### E05 · manifest 文件名三种写法（.json / .jsonl）互相不一致
- **日期 / 环境**：2026-10-15 · 代码审查发现
- **症状**：`SKILL.md` 与 `detect.py` 写 `install-manifest.json`，
  `install.sh` / `rollback.sh` / `docs/04` 写 `install-manifest.jsonl`。
  契约里的 `"manifest"` 字段指向一个**永远不会被创建**的文件。
- **根因** `[实测]`：改名（json → jsonl）时只改了一半。回滚本身不受影响
  （rollback.sh 读 .jsonl 是对的），但按契约路径去找会找不到。
- **修法**：统一为 `install-manifest.jsonl`（append-only 的 JSONL 才是本意）；
  契约字段与 SKILL.md 同步改正。
- **证据**：`grep -rn 'install-manifest' skills/ docs/`。
- **状态**：已根治

### E06 · make-tts-track.py 默认文件名残留旧项目 passthrough-intro
- **日期 / 环境**：2026-10-15 · 代码审查发现
- **症状**：`SRT` 默认 `$PWD/out/passthrough-intro.srt`、`BASENAME` 默认
  `passthrough-intro-voice` —— 本项目叫 Ideaform，这两个默认值是

- **根因** `[实测]`：复制改造遗留。
- **修法**：默认值改为中性的 `ideaform-intro-voice` / `ideaform-intro.srt`
  （demo 的 out/ 里实际用的就是这个名字，改后与既成事实一致）。
- **证据**：`make-tts-track.py:32,57,59`；`examples/demo-episode/out/ideaform-intro-voice.wav`。
- **状态**：已根治

### E07 · verify.py `--only` 传重复项会把"全过"误判为"未过"
- **日期 / 环境**：2026-10-15 · 代码审查发现
- **症状**：`verify.py --only tts,tts` 时 `passed` 要求
  `len(results) == len(only)`（集合去重后 results 只有 1 条，only 有 2 个值），
  恒为 False。
- **根因** `[推断]`：`only` 是集合（自动去重），等式右边却按原始 split 计数。
- **修法**：等式右边改为去重后的数量：
  `len(results) == len({s.strip() for s in args.only.split(",") if s.strip()})`。
- **证据**：`verify.py` main() 的 passed 计算行。
- **状态**：已根治

### E08 · Remotion 渲染时照片全 404（裸相对路径）
- **日期 / 环境**：2026-10-15 · 桂花片 · Remotion 4.0.515
- **症状**：stderr 刷 `localhost:3000/photos/dan1.jpg 404`，成片里照片全裂；still 抽帧同样中招，
  但抽帧图看不出（当时模型无图像输入，见 E18）→ 一直漏判，直到基准渲染打日志才暴露。
- **根因** `[实测]`：act 组件里写成裸相对路径 `src="photos/x.jpg"`。
  Remotion **渲染模式下 publicDir 不按相对路径服务**（studio 里能显示只是假象）。
- **修法**：一律 `staticFile("photos/x.jpg")`；把 stderr 里 `404|Failed to load` 的计数当验收项，别只信退出码。
- **证据**：`act1.tsx:68`、`act4.tsx:195` 改前；修复后基准渲染失败计数 0。
- **状态**：已根治（代码侧 + 验收项）

### E09 · `-shortest` 把视频尾部多砍 13 帧
- **日期 / 环境**：2026-10-15 · 桂花片 · 路线 B 后合成
- **症状**：后合成后帧数 **10066 → 10053**，verify V1 挂。
- **根因** `[实测]`：`-shortest` 配合 AAC priming——音频流实际结束点早于容器报告时长，ffmpeg 按较短的音轨截断视频。
- **修法**：`mix-av.sh` 去掉 `-shortest`。音轨长度已由 `amix duration=first` 限死；
  流水线里帧数本就由 TTS 音轨导出（voice ≤ video），不会音频超长。
- **证据**：修复后帧数 10066、音轨 192 kbps、时长一致。
- **状态**：已根治（脚本侧）

### E11 · `npx tsc --noEmit` 假阳性（退出 0，但根本没跑真 tsc）

### E12 · Bash 工具的 cwd 不跨命令保持
- **日期 / 环境**：2026-10-15 · 本沙箱
- **症状**：每条命令 cwd 都被重置回工作空间根；`cd` 只在本条命令内有效 →

### E13 · 自创强调色 ≠ 规范强调红 → 封面像素校验假失败
- **日期 / 环境**：2026-10-15 · 桂花片封面
- **症状**：封面校验 P6 判「强调色（红/橙）像素 0」，但图上斜线/色块/kicker 明明有颜色。

### E15 · `amix` 默认 `normalize=1`，成片静默掉 6 dB
- **日期 / 环境**：2026-10-15 · 桂花片混音
- **症状**：成片峰值 **-6.69 dBFS**，比解说轨既定 -1.00 dBFS 低约 6 dB；
  但旁白/BGM **相对平衡正常**，听感"不算错"→ 长期漏判。
- **根因** `[实测]`：`amix` 默认 `normalize=1`，把每个输入各除以输入数（2 路 → **-6.02 dB**），
  旁白与 BGM 一起被压。
- **修法**：`mix-av.sh` 显式 `normalize=0`；并改**两遍法**——先只混音轨（不编码视频，秒级）
  实测真实峰值 → 按 `--peak`（默认 -1.0 dBFS）算 headroom 再套 `volume`，
  既不削波又精确落在目标峰值。
- **证据**：`mix-av.sh` 的 `peak_db` / `peak_trim` 与混音探针段。
- **状态**：已根治（脚本侧）

### E16 · 自造「成片几分钟」选择题 —— 违反本 skill 的顺序铁律
- **日期 / 环境**：2026-10-15 · 桂花片开工阶段
- **症状**：模型用 AskUserQuestion 让用户在「标准版·约 7 分钟」等选项里**选成片时长**，
  随后把"7 分钟"当成硬指标去追。
- **根因** `[实测]`：**本 skill 全文没有任何"问用户要时长"的话术**
  （`grep -rn '标准版\|几分钟' skills/ docs/` 无命中）。SKILL §3「顺序铁律」写明：
  **时间轴从 TTS 真实语速里长出来**——时长是**输出**，不是**输入**。
  阶段一只有"文稿给用户确认"（确认对象是**文稿与层次**）；模型把它误读成"总时长确认"，
  并自造了选项。
- **修法**：**禁止索取成片时长**。只报「按这份文稿，实测 X 分 Y 秒」。
  用户要更长/更短 → 改的是**文稿**，不是时间。（已写入 SKILL §3 铁律段）
- **证据**：SKILL.md §3 及其"先写死时间码 → 被迫压缩 1.218x"的反例。
- **状态**：已记（本条即防线）
