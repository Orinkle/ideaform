# 03 · 路径契约（两个 Skill 之间怎么传递工具链路径）

> 这是本项目最关键的设计。用户明确要求「特别注意工具链路径的传递、两个 Skill 之间的衔接」。

---

## 1. 为什么不直接互相 import

最直觉的做法是让工作流技能去读环境配置技能里的路径。**这是错的**：

- 环境配置技能是**一次性**的（用完要禁用/删除）→ 它一走，工作流就哑了
- 两个技能可能装在不同位置、不同版本 → 路径耦合脆弱
- 换机器时配置文件该被覆盖，但技能目录不该被乱动

**解法：两者不直接依赖，而是各自与一个中立的第三方文件通信。**

```
┌─────────────────────┐        writes         ┌──────────────────────────┐
│ constructivist-     │ ────────────────────→ │  ~/.config/              │
│ video-env           │                       │  ideaform/   │
│ （一次性，用完即弃） │                       │    toolchain.json  ★契约 │
└─────────────────────┘                       │    env.sh                │
                                              └───────────┬──────────────┘
                                                          │ reads
                                              ┌───────────▼──────────────┐
                                              │ constructivist-           │
                                              │ video-workflow（长期）    │
                                              └───────────────────────────┘
```

**契约文件在两个 Skill 的目录之外** —— 这是刻意的。
删掉 `ideaform-setup` 不会碰到它，工作流照常工作。

## 3. 工作流的起步检查（三条）

```bash
CONTRACT="${VW_CONTRACT:-$HOME/.config/ideaform/toolchain.json}"
```

1. **存在吗？** 不存在 → 让用户先跑环境配置技能。
2. **`schema_version` 认识吗？** 不符 → 要求重跑环境配置技能。
3. **`verified_at` 是 `null` 吗？** 是 → 警告"环境未通过冒烟校验"。
   并且 `tools.lmms.stkdir_ok` 必须为 `true`（否则 BGM 全程静音）。

工作流技能（`ideaform`）的 §0 就写了这三条。

## 4. 消费方式

### 方式 A · shell 取变量（推荐）

```bash
source "$(dirname "$CONTRACT")/env.sh"
# 之后可直接用：$VW_NODE $VW_VENV $VW_PYTHON $VW_FFMPEG $VW_FFPROBE
#               $VW_REMOTION_PROJECT $VW_CHROME $VW_LMMS_APPRUN $VW_TMPDIR
```

`env.sh` 还带一个取值函数：

```bash
vw tools.remotion.version      # → 4.0.515
vw tools.lmms.stkdir_ok        # → True
vw _summary.ready              # → True
```

### 方式 B · 脚本内读 JSON

本项目的 Python/Bash 脚本都**优先读契约**，读不到再退回自动发现：

```python
_CONTRACT = os.environ.get("VW_CONTRACT") or "~/.config/ideaform/toolchain.json"
if os.path.exists(_CONTRACT):
    t = json.load(open(_CONTRACT))["tools"]
    os.environ.setdefault("FFMPEG",  t["ffmpeg"]["path"])
    os.environ.setdefault("FFPROBE", t["ffprobe"]["path"])
```

（`make-tts-track.py` 开头就是这段。）

## 5. ⚠️ 路径传递的头号坑：**不要 `resolve` 软链**

**实测踩过。** 托管工具链的路径里含软链：

```bash
ls -la ~/.workbuddy/binaries/python/envs/default/bin/python
# lrwxrwxrwx  ... python -> python3
readlink -f ~/.workbuddy/binaries/python/envs/default/bin/python
# /opt/WorkBuddy/resources/runtime/python/bin/python3.13     ← 已经不是 venv 了！
```

`Path.resolve()` 会把 venv 解释器解析到系统 python →
**`sys.prefix` 随之改变 → venv 里装的包全部 import 不到**：

```
ModuleNotFoundError: No module named 'edge_tts'
```

而 `edge-tts` 明明就装在那个 venv 里。

**规则**：

- 路径一律用**原样（absolute，不 resolve）** 传递与执行。
- 契约里额外给一个 `real` / `python_real` 字段**仅供诊断展示**，不用于执行。
- 探测脚本用 `os.path.abspath()` 而不是 `Path.resolve()`。

`detect.py` 已按此实现，并在报告里显式提示：

```
  · 注      venv 解释器经软链 → /opt/.../python3.13（执行一律用原路径，勿 resolve）
```

---

## 6. ⚠️ 另一个坑：`AppRun` 也是软链

```
squashfs-root/AppRun -> usr/bin/lmms
```

`resolve` 之后 `parent` 就变成 `squashfs-root/usr`，
再推导 `stkdir` 会得到 `.../usr/usr/share/stk/rawwaves`（**多了一层 `usr`**），
于是报"stkdir 不一致"，而且**修的方向也会错**。

**正解**：`root = Path(apprun).parent`（= `squashfs-root`），不做 resolve。

---

## 7. `tmpdir` 为什么要进契约

本机 `/tmp` 是 **10MB tmpfs**。Remotion 打包、`pip install`、AppImage 解包
**都会写 `TMPDIR`** → `ENOSPC: no space left on device`。

所以探测脚本会挑一个剩余空间 > 2GB 的目录作为 `tmpdir` 写进契约，
工作流的所有脚本都读它：

```bash
export TMPDIR="$VW_TMPDIR"
```

**"No space left on device" 不一定是磁盘满，先看 `TMPDIR`。**

---

## 8. 契约的失效与刷新

| 情况 | 要做什么 |
|---|---|
| 换工作空间 | 什么都不用做（契约是机器级的） |
| 重装 / 升级了某个工具 | `detect.py --write` → `verify.py` |
| 换机器 | 重跑整个环境配置技能 |
| 契约被误删 | `cp` 备份回来（`rollback.sh --purge-contract` 会留备份） |

刷新契约**总是安全的** —— 它只写 `~/.config/ideaform/` 下的两个文件。
