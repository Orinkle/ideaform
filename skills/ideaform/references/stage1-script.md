# 阶段一 · 文稿（分层是硬要求）

---

## 1. 输入 / 输出

**输入**：用户给什么就用什么 —— 一个主题、一段材料、一个口头想法、一份文档、
甚至一个链接。**不要要求用户提供"标准格式"**。

**输出**：

| 文件 | 用途 |
|---|---|
| `script.md` | 完整文稿，**显式标出论述层次**（人读、给用户确认） |
| `台词.txt` | 一行一句的口播台词，**只含要读出来的字**（给 TTS） |

---

## 2. 分层：不是为了好看，是阶段三的输入

```
## 层次 1 · 引入
这是《文稿即时间轴》的第一层。
解说音轨才是整条流水线的时间主轴。
## 层次 2 · 展开
画面帧数由它决定，不是反过来。
第二层开始了，音乐在这里变奏。
## 层次 3 · 收束
层次切换用变奏表示，而不是换一首曲子。
最后收束回主调。
```

**没有层次标注，BGM 变奏就没有着力点。** 阶段三要把这些层次映射成
`present / develop / intensify / contrast / resolve / sustain` 六个叙事功能。

经验：**3~6 层**最好。少了没起伏，多了变奏会被稀释。

---

## 3. 写台词的六条规矩（直接影响 TTS 与画面）

1. **一句 = 一个语义单元。** 别把两件事塞进一句 —— TTS 按句排轴，塞了槽位会拖长。
2. **单句 8–30 字。** 过长拆句（TTS 断句会怪），过短合句（节奏太碎）。
   中文口播约 **4.5–5.5 字/秒**，22 字 ≈ 4.3s。
3. **一句以句号/问号收尾。** 帮助 TTS 断句。不要用分号连一句。
4. **写"听得懂"的话，不是"看得懂"的话。**
   - ✅「画面帧数由它决定，不是反过来」
   - ❌「帧数确定依赖 TTS 之自然语速基准」
   书面语在口播里会变成一团。**朗读一遍**，读不顺就重写。
5. **数字与符号慎用。** TTS 读 `1.218x` 会怪。写「一点二一八倍」或「约一点二倍」。
   英文缩写（API、JSON）确认 TTS 读得对，必要时写成中文。
6. **层次切换处给一句"路标"。** 例如「第二层开始了」——
   这句本身就是阶段三的变奏边界锚点，听众也被明确导航。

---

## 4. 让音乐能"挂住"文稿

因为 BGM 要在层次边界变奏，**文稿的层次边界要清晰、可指认**。
写完 `script.md` 后，检查：

- 每个层次的**第一句**是不是一个明确的转向？（不是"另外"这种软过渡）
- 相邻层次之间**有没有实质变化**？（如果只是"继续说"，那不该算新层次）

如果某两层其实是一层，**合并它**——否则音乐会在没有变化的地方硬变奏，反而奇怪。

---

## 5. 反例：什么文稿会让后面全乱

| 反例 | 后果 |
|---|---|
| 一段到底、没有层次 | 阶段三无从下手，BGM 只能平铺 |
| 单句 50+ 字 | TTS 槽位过长，画面留白太多 |
| 层次之间没有实质差异 | 变奏变成噪音 |
| 大量书面语/缩写 | TTS 读错、听众听不懂 |
| 句子数与层次数不匹配（如 30 句 2 层） | 变奏点太稀疏，BGM 沉闷 |

---

## 6. 出口 → 下一步

1. 把 `台词.txt` 给用户过一遍（或直接跑 TTS，让其听 MP3 便捷版）
2. **改完台词必须重跑阶段二** —— 因为时间轴是从台词长出来的，
   改一句会让后面所有 cue 的 `start/end` 平移

```bash
"$VW_VENV/bin/python" scripts/make-tts-track.py --lines 台词.txt --fps 30 --audio \
    --plan-out out/plan.json --ts-out out/timeline.ts
```

> ⚠️ TTS 的缓存键带**内容哈希**，所以改台词不会误用旧音频。
> 但**画面侧的 `timeline.ts` 必须同步更新**（`cp` 进 Remotion 工程），
> 否则画面还停在旧帧数上 —— 这是最常见的"改了台词但画面没跟上"的成因。
